# consistency-check: 未検証サマリと検証結果ドラフト

全出力の検証は非現実的なので、検証の深さをリスクに比例させる。

- 機能A 未検証サマリ: 調査結論を未検証と明示して記録に残す(検証はしない、まず残す)
- 機能B 検証結果ドラフト: 主張を絞って URL と照合し、記入済みの検証結果として提示する。
  ユーザーの作業は「URL を開いて追認し、転記する」だけにする(記載の最終責任はユーザー)

典型的な流れ: 調査 → A を記録 → B で検証 → ユーザーが一次確認 → 打ち切り。A・B 単独でも呼ばれる。

## 機能の選択

- 引数 `summary` → A、`verify` → B(引数が最優先)
- 「まとめて」「要約」「記録に残したい」→ A。「整合性チェック」「一次確認」「打ち切っていいか」→ B
- 迷ったら A → B の順で両方提案する

共通の形式:

- 指示がなければ textile。Notion・勉強会向けと明示されたときのみ markdown(見出しは h2 相当から)
- 文字装飾なし。1 項目は必ず 1 行、途中で改行しない(textile はリスト項目内の改行で崩れる)。
  分量の目安は 1 項目 50 字(原文引用は含めない)。超えそうなら内容を絞る
- textile の丸カッコは全角（）(半角は Acronym 判定で装飾化されるため)。マクロ構文・URL 内は半角のまま

## 機能A: 未検証サマリ

- 見出しは「h3. claude で下調べ: <調査内容>」に固定(AI の下調べ段階で確定情報は別、と初見でも伝わる)
- 接続文 1 行の後、本文(表・結論・出典 URL)は `{{collapse(表示)}}` で折りたたむ。
  分量は会話の最終成果物からさらに一段削り、経緯・ボツ案は含めない
- 末尾に TODO 行で検証への導線を埋め込む。検証対象は「主要な主張」のような抽象語でなく、
  真偽が判定できる命題として 1〜2 件、本文から抜き出す(選定基準は機能B と同じ)。
  数値を伴う主張は数値ごと書く(「速い」ではなく「週 4 回で CPA 3,000 円」)
- 命題は意思決定における役割の対から選ぶ: 下限/上限、前提/結論、実在性/適用条件。
  該当する対があれば両側から 1 件ずつ、なければ最重要 1 件だけ

```textile
h3. claude で下調べ: <調査内容>

<接続文 1 行。未検証である旨を明示>

{{collapse(表示)

<要約本文(表・結論・出典)>

}}

TODO: 「<命題1>」「<命題2>」を一次情報で整合性チェック
```

## 機能B: 検証結果ドラフト

### 絞り込みと情報源

- 基準は「間違っていた場合に手戻り・対外説明が発生するか」。2〜3 件、参考情報は含めない。
  絞れないときは「今回の意思決定は何か」をユーザーに確認する
- 情報源は少数に集約する(確認先の数 ≠ 主張の数。1 情報源で複数主張を検証できる組み合わせを優先)
- 一次情報を優先: 公式ヘルプ・ドキュメント > 公式ブログ・プレス > 論文本文 > 二次解説
- 成果物単体で自己完結させる。未検証の表・要約(機能A の note 含む)への参照は禁止

### モード

- 比較型(他社・論文比較): グループ = 比較対象。「実在すること」の確認が中心。
  論文は abstract / 該当節・図表番号まで指定する(全文読ませない)
- 正誤型(単一テーマの真偽): グループ = 論点。支持する記述と反証しうる記述の両方を探す
  (確証バイアス対策)。判定は 真 / 偽 / 条件付き
- 迷ったら比較型で作り、モードを明記する

### セルフチェック(提示前に必須)

各項目を読み取り専用サブエージェント(web-researcher 等)で URL と照合してから提示する。

- 相違あり(記述が見つからない・内容が異なる)は記載と元の結論の両方を修正して提示し、
  修正した旨は会話内で伝える(成果物には書かない)
- アクセス不可(ログイン必須等)があった場合のみ、末尾にその旨を簡潔に記載する

### 出力フォーマット

```textile
h3. <対象領域>の確認: <対象名>

<何を対象に何を検証したかの 1 文>
結論、<検証から言える主張。制約・条件があれば簡潔に補足しつつ、詳細は結果に委ねる>

確認先:

* <ページタイトルや論文タイトル>: <URL>

結果: 以下を確認

* <テーマまたは主要な確認事実>（<場所目安>: "<Ctrl+F で探せる原文引用>"）
** <配下の確認事実>（<場所目安>: "<原文引用>"）
*** <厳選した補足(具体値・条件)>
```

- 冒頭 2 行は文章として続ける。「結論、」は読点のまま、コロンに直さない
  (概要+結論の文章であり、「確認先:」等の構造化セクションと意図的に区別している)
- 確認先は実際のページ・論文タイトルを書く。「NBD の論文」のようなジャンルだけのラベルは禁止
  (表題との一致が追認の起点)。長い論文タイトルは副題を省略可
- 各行に場所目安+原文引用を付ける(URL を開いて数分で追認できる粒度)。
  場所目安は章・節名、なければ「冒頭」「"xxx" の項目」等。長い章タイトルは先頭 10 文字+「…」
- 結果はテーマごとの 2 階層が基本(事実が少数なら 1 階層で可)。
  3 階層目は価値ある補足(具体値・条件)に限り、厳選する
- 「存在しないこと」の確認は、探した語と出現状況を明記する
- 書かないもの(最終責任がユーザーにあることを曖昧にする・余計な前提を感じさせるため):
  「AI 照合済み」等の AI への言及 / 「すべて確認」等の網羅表現 / 選定理由 / 残タスク行

### 例(比較型・textile)

```textile
h3. DSP の確認: Amazon DSP

DSP のリーチ目標商品として Amazon DSP を対象に検証した。
結論、前例は実在する。ただし、「UU 絶対数の保証」ではなく「頻度目標を入力し予算内で UU を最大化する」形（対象キャンペーンも限定）

確認先:

* Amazon DSP Goal-based bidding 告知: https://advertising.amazon.com/en-us/resources/whats-new/amazon-dsp-goal-based-bidding （2024-09-19 付）

結果: 以下を確認

* 目標入力について
** KPI に UU リーチ最大化を選べる（本文冒頭: "achieve higher unique user reach"）
** 頻度目標を数値で入力できる（設定例の段落: "a target frequency of 2 times per week"）
*** 対象はディスプレイ・非保証動画キャンペーンに限定（"display, and video non-guaranteed campaigns"）
* 保証について
** 未達時の保証・補填の文言は存在しない（全文検索: "guarantee" は non-guaranteed のみ、make-good なし）
```

## やらないこと

- ユーザーの一次確認の代替(セルフチェックは事前照合まで。最終確認はユーザーが行う)
- 追加調査(通常の調査依頼として別途行う。セルフチェックは既出 URL との照合に限る)
