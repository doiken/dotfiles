# 作業再開メモ出力

数日後に同じセッションを再開することを想定し、記憶があいまいでも作業を再開できる引き継ぎメモを生成する。

## 想定読者

- 数日〜数週間後の自分
- コード差分や git log を見れば一部は思い出せるが、判断の経緯やユーザーから受けた口頭の指示は残っていない

→ コードから読み取れない情報を中心に残すことが価値の源泉。

## 出力ルール

`note` スキルと同様、転記しやすい構造を保つ。

- 表・リスト中心、1行は概ね 50 字以内
- 冗長な説明・前置きは不要
- 見出し（##, ###）で構造化する
- 関連ファイルは `path:line` 形式で記載しナビゲート可能にする
- リンク（PR・チケット）はそのまま含める

## 出力テンプレート

```markdown
# 作業再開メモ — {{topic}}

最終更新: {{YYYY-MM-DD}}
作業ディレクトリ: {{cwd}}

## 概要
100 字程度でセッション全体の目的・現在地を要約。

## やったこと
| # | 内容 | 関連ファイル/PR |
|---|------|-----------------|
| 1 | ... | path:line       |

## TODO
| カテゴリ | 内容 | 補足 |
|----------|------|------|
| 保留     | ...  | 保留にした理由 |
| 途中     | ...  | どこまで完了したか |
| 承認待ち | ...  | 何の判断が必要か |
| 未検証   | ...  | 検証方法 |

## 次のアクション
1. 再開時に最初にやるべき具体的な動作
2. ...

## コンテキスト
- コードから読み取れない前提・経緯（後述の指針参照）
```

## TODO カテゴリの定義

該当するものだけ書く。該当しないカテゴリは行ごと省略する。

- **保留**: ユーザーが明示的に「後で」と判断した作業
- **途中**: 部分的にしか完了していない実装。"どこまで完了したか" を必ず書く
- **承認待ち**: ユーザーの判断・承認待ちで進められないステップ
- **未検証**: 実装は完了したがテスト・動作確認ができていない項目

## 「コンテキスト」欄に書く情報

後日の自分が最も忘れやすく、かつコードを見ても復元できない情報を残す。

- 試したが採用しなかったアプローチと却下理由
- ユーザーから受けた口頭の指示・好み（コメントとして残さなかったもの）
- 関連チケット / PR / issue 番号 / スレッド URL
- 前提となるコマンド・環境変数・実行手順
- デバッグ中に発見した非自明な挙動

## 「次のアクション」の書き方

抽象的な動詞ではなく、具体的なファイル・関数・操作で書く。

**Bad**: 「テストを修正する」
**Good**: 「`tests/test_foo.py:42` の `test_bar` を `mock` から `fixture` 形式に置き換える」

**Bad**: 「リファクタリングを進める」
**Good**: 「`api/handler.py` の `process()` を `validator.py` に切り出し、ユニットテストを追加」

## 保存先

引数で出力先が指定されていればそこへ書き込む。指定がなければ作業ディレクトリ直下に `RESUME.md` として保存する。

既存の `RESUME.md` がある場合は上書きせず、内容を確認したうえで以下のいずれかをユーザーに提案する:
1. 新しい日時のセクションとして追記
2. 別ファイル名（例: `RESUME-2026-05-01.md`）で保存
3. 上書き

## 出力前のセルフチェック

- やったことに「試したが破棄したアプローチ」が混じっていないか（→ コンテキスト欄に移す）
- TODO の各行に "なぜ" や "どこまで" が入っているか
- 関連ファイルが `path:line` 形式で書かれているか
- 1行が長すぎないか（50字目安）
