# merge — 別セッションの結論を取り込む

<!-- 厳密には squash では?という指摘は受け付けていません -->


## 目的

意図的に分散させたセッション(フォーク・並行作業)の成果を、会話ログ全文ではなく「消化済みの結論」だけ現在のセッションに還流させる。

全文を取り込まない理由: ログ全文はこのセッションのコンテキストを汚染し、ユーザーの読解負荷も増やす。要約は**相手セッション側で行わせる**(相手は自分の文脈を全部持っているので要約に最適な立場であり、こちらのコンテキストを消費しない)。

## 登場する識別子

| 識別子 | 例 | 実体 | merge での用途 |
|---|---|---|---|
| **SESSION_ID** | `23a0d13d-…` | transcript のファイル名。会話単位 | **引数として受け取るのはこれだけ** |
| **peer name** | `work-a7` | `~/.claude/sessions/<PID>.json` の `name`。プロセス単位 | SendMessage の宛先。手順 1 で解決する |
| ref | `0a4941` | ListAgents の表示のみ。どこにも保存されない | 使わない |

peer name はプロセス単位、SESSION_ID は会話単位なので **1 対 1 とは限らない**(後述の fork 参照)。

## 引数

**SESSION_ID のみ**を受け取る。UUID で、**プレフィクスでよい**(一意に定まる長さなら可)。

peer name は引数として受け付けない。UUID プレフィクスと見分けがつかず、誤った宛先に送る恐れがあるため。

## 手順

### 1. peer name の解決

`<PREFIX>` を引数の SESSION_ID で置き換えて次を実行する:

```
jq -rs --arg sid "<PREFIX>" 'map(select(.sessionId|startswith($sid))) | max_by(.updatedAt // .startedAt) | .name' ~/.claude/sessions/*.json
```

`~/.claude/sessions/` は稼働中セッションのレジストリ(1 プロセス 1 ファイル、ファイル名は PID)。**`~/.claude/projects/` は走査しないこと**(巨大な transcript 群で、ここに peer name は無い)。

fork で SESSION_ID が重複していても `updatedAt` 最大(直近まで動いていた側)が選ばれる。`updatedAt` は起動直後のセッションには存在しないため `startedAt` で代替している。

- **peer name が返った** → 手順 2 へ
- **`null` が返った** → 相手セッションは終了している。レジストリはプロセス終了時に削除されるため、残っていなければ確実に終了済み。ソケット(`/tmp/cc-socks/<PID>.sock`)は残骸が残るが接続できず、ListAgents にも出ないので SendMessage は届かない。`claude --resume <SESSION_ID>` での再開をユーザーに案内して終了する

### 2. 結論の要約を依頼

SendMessage で依頼する。形式と分量を先に固定するのが重要(相手も LLM なので、指定しないと長文が返ってくる)。

行数上限の目安: 基本 30 行。相手セッションが複数トピックを扱っていそうな場合は「1 トピックあたり 15 行、合計 60 行以内」とする。

```
このセッションの成果を現在の別セッションに取り込みます(merge)。
以下の形式で返信してください。経緯の全文転記は不要、合計 30 行以内で。

- 結論:
- 根拠(要点のみ):
- 成果物・参照(ファイルパス・URL):
- 未解決・保留:
```

### 3. 返信の受け取りと提示

返信は相手セッションからの受信メッセージとして届く。届いたら:

- `## Merge: <peer name>` の見出しを付けてユーザーに提示する
- 以後、この内容を現在の会話の文脈として扱う

数分待っても返信がない場合は、相手セッションが承認待ち等でブロックしている可能性をユーザーに伝える(相手のターミナルを見てもらう)。返信を捏造・推測しないこと。

### 4. 取り込み後の深掘り

さらに詳細が必要になったら、相手に全文を送らせるのではなく、返信の「成果物・参照」に挙がったファイルを直接 Read する。追加の質問は再度 SendMessage で相手に聞いてよい(文脈は相手側に保持されている)。

## 補足: fork と SESSION_ID の重複

`claude --resume <ID>` は既定で **SESSION_ID を再利用する**。この状態で 2 つのプロセスを同時に走らせると、同じ SESSION_ID を持つセッションが複数存在し、1 つの transcript に 2 本の枝が交互に追記される(枝は `parentUuid` で分離されるため会話内容は混ざらないが、枝ごとの識別子は存在しない)。

弊害:

- SESSION_ID から peer name が一意に定まらない(手順 1 の「複数見つかった」)
- `/resume` の一覧は transcript ファイル単位のため、**どちらの枝を再開するか選べない**(最後に書き込まれた葉が選ばれる)

分岐させるときは `claude --resume <ID> --fork-session` を使うこと。新しい SESSION_ID が振られて transcript が別ファイルになり、上記の曖昧さが両方とも消える。ユーザーが fork 相当の操作を相談してきたらこれを案内する。
